## Changes and interfaces

- `movement.correct {movementId,replacementQuantity,reason}` appends a `movementCorrections` entry referring to the immutable original movement. Entries preserve effective before/after quantity, reason, operation ID and revision. `movementQuantity` supplies the latest effective value; `stockSummary` and therefore purchasing opening-stock credit use that value. The original 100 remains 100, correction to 10 calculates as 10, a later correction replaces the effective 10 rather than adding another independent delivery. Negative quantities, missing targets, empty reasons and no-effect corrections are rejected.
- `sales.correctPrice {saleId,priceCents,reason}` appends `salePriceCorrections`; the stored sale price remains unchanged. `salePrice` / `effectiveSales` drive all Analysis displays and revenue calculations. Original 50 cents corrected to 500 cents, followed by a menu master price of 900 cents, still produces 1000 cents for two sales. The old missing-price command cannot overwrite a sale already corrected from null.
- `invoice.correct {invoiceId,changes,reason}` whitelists economic and assignment fields. No source, local path, baseline, status or history injection is permitted in its changes. Explicit correction can correct imported original economics, with the original facts retained in the immutable baseline and before/after events. Existing `invoice.update` / `invoice.link` remain compatible commands but any change now needs a reason and writes the same protected history. The receipt editor sends the explicit correction command and requires the reason.
- Every newly created manual receipt stores its first confirmed snapshot in the existing additive `sourceBaseline` field, even without `source`. For an older receipt lacking a baseline, the first new correction preserves the currently known prior snapshot. This is described as the first preserved state, without fabricating an earlier historical origin, actor, time, imported file or missing corrections. The old source-less exemption is removed from both reducer and server invariants. Removal of a manual receipt, source removal/swap/addition, changes to original local path, baseline replacement, history trimming/rewrite, incorrect before/after, and direct candidate changes without a history event are denied. Nullable-field normalization is also recorded when it changes the actual stored snapshot.
- `order.mark {orderId,status:'bestellt'|'bestaetigt',note}` permits only prepared → ordered → confirmed. The optional confirmation follows an actual ordered marker. Each status is appended to `statusHistory`; order lines/groups/totals/context/timestamp/order ID remain immutable. Unknown versions, backwards/skipped/duplicate new transitions and history edits are rejected. This records the user's manual supplier contact; no sending or messaging integration is called.
- `orderPlanningChanged` detects live order lines and delivery date/address/contact differences from the saved version. Prepared versions show the warning, manual status action, and status history. A changed plan does not overwrite the ordered version.
- Correction dialogs are reachable in Deliveries (including historical-location stock overview), Analysis and Receipts. History shows original/effective values, reason and confirmed actor/time. The existing modal portal, focus handling, form draft protection, responsive tables/cards and Money/Quantity components remain in place. A shared `CorrectionDialog` uses that modal and waits for the commit result before closing.

## Server boundaries

- Protocol 2 and the public Custom API JSON-string signatures stay unchanged. Operation allowlist adds the four commands. Exact request hashing, immutable receipt rows, transaction, CAS, caller/environment identity, event targeting, effective WriteAccess, owner-only configuration/closure checks, v1 quarantine and 512 KiB aggregate cap are retained.
- `EconomicHistory.cs` is a partial `StatePolicy` helper for correction chains, order history and stamping. Candidate semantics are checked before and after stamping, independently of operation labels. New entries receive the authenticated `actor` GUID and one server UTC timestamp shared with the immutable commit receipt. Browser-supplied operation ID, revision, actor and time cannot become authoritative. Previous metadata is compared verbatim and cannot be replaced. Existing historical entries without actor/time remain visibly unconfirmed.
- Original movements are still fully append-only. Original sales price remains protected. Correction chains require an existing target, exact effective previous value, valid non-negative replacement, nonempty reason, immutable prefix and at most one new correction per history collection per commit. Server metadata normalization does not alter previously stored entries.
- Orders remain in their original array positions with their full immutable snapshot. Only valid appended status history changes the displayed status. The earlier generic append-only order check now excludes just these two status fields; a dedicated history invariant protects them.
- Scope checking also denies creation of a new event carrying posted movements, sales, receipts, orders, lessons or correction history. This closes an owner candidate-state path that could otherwise manufacture an unconfirmed past while creating a new event; normal event creation still starts empty and preserves every prior event.
- New/manual receipt baselines are required on creation and protected thereafter. All source-less prior receipts are included in the same transition checks as imported receipts. Old legacy correction entries remain readable without invented after/actor/time fields; newly appended corrections require reason and exact before/after.

## Migration / compatibility

Stored Microsoft schema stays 2. Optional `movementCorrections`, `salePriceCorrections`, order `statusHistory`, and receipt audit fields are additive. Existing imports, archive originals, receipt rows, previous correction entries and operation signature bytes were not rewritten. Existing `sourceBaseline` is reused for manual receipts to avoid silently renaming or losing historical fields.

No bulk migration runs on load. Missing legacy receipt baseline is materialized only when a new correction actually occurs and only from the known prior state. Newly entered manual receipts preserve their baseline immediately. Historical omissions cannot be reconstructed and are not presented as known.

The actual local file is a legacy local schema-1 envelope, revision 34, with two events. Microsoft policy correctly rejects those raw bytes. A separate read-only test projects **only schemaVersion to 2 in memory** for root and archive to inspect the actual corpus's closed fields; it is not a conversion, deployment or acceptance of raw schema 1. This legacy local file is not the cloud state, and no stored-server migration has been tested. No ordinary domain operation globally normalizes schema or historical fields; receipt nullable normalization occurs only within the requested receipt correction and is itself recorded. Both source file and parent's backup remain byte-identical, SHA-256 `09ac7edb02e899618bb6a802c33056d0460c5c428258e96739e4d4a26734d300`.

Other tasks should use `movementQuantity`, `salePrice` / `effectiveSales`, and current receipt values for effective calculations, retaining the original records and histories. Receiving/closure (Task 4) and document tables/storage/recognition (Tasks 5/6) were not implemented here. New document metadata will need an explicit additive closed-schema review. Actor display currently uses the confirmed stable user GUID, because no verified display-name mapping is exposed; the UI does not invent a person's name.
