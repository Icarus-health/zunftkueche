## Interfaces and behavior

- `buildReceivingList(state, orderId)` uses immutable saved order lines and their IDs. It returns ordered, confirmed received, remaining, deviation and linked entries. No posted entry means actual received/deviation are **null**, not zero. Explicit zero acceptance remains distinguishable. The original order snapshot never changes. Effective receipt quantities use `movementQuantity`, including later corrections.
- `delivery.accept {orderId, day, location, lines:[{lineId,articleId,quantity,substitutionConfirmed?}], note}` is an explicit acceptance command. It appends one movement per supplied line with stable `operationId:index` IDs, `orderId`/`orderLineId`, day/location and note. It never copies Soll quantities automatically. Different articles require explicit substitution confirmation, nonempty note and the same article unit; it does not invent a conversion. Multiple partial deliveries accumulate; exact retries retain the prior result without duplicate inventory. A 120 order with 110 accepted shows 10 remaining; a later accepted substitute closes that remainder, while a later correction updates it accurately.
- Receiving UI is a saved-order list above the existing warehouse capture. A per-position modal starts with an empty actual quantity, supports active locations/day/substitute/note and waits for commit confirmation. The list retains per-entry article, effective amount, day and note. Existing inventory, corrections, history locations and draft/focus guards remain.
- `plan.allocate {id, allocations:[{day,time,quantity}]}` adds a bounded delivery allocation to the existing plan row without overwriting its original total or source. The editor shows original total, allocated total, remainder and overcoverage and permits multiple windows. Allocated rows become explicitly manual weekend procurement. `prepareOrder` materializes each confirmed allocation using stable `planId:allocation:index` line IDs, selected day/time and its actual quantity. Saved old snapshots remain intact. Purchasing coverage counts confirmed allocation totals, preserving imported/manual totals as original facts. Empty allocations return ordering to the original row's schedule.
- `drink.configure {menuId, mode:'direct'|'variants'|'manual', lines}` distinguishes one direct article per sold unit, explicitly confirmed weighted alternatives whose fractions total exactly 1, and manual purchasing with no automatic recipe. Duplicate/nonpositive/missing article assignments are rejected. An unclassified drink collection never produces simultaneous demand for all listed alternatives. Manual/unresolved drinks remain open in automatic purchasing; the recipes screen does not show their additive cost as confirmed. The editor makes the choice explicit and requires its confirmation checkbox for direct/variants. Existing food recipe editing remains available. Switching a food back to its recipe removes its prior supply-mode marker.
- `buildClosureChecklist(state,scope)` checks menu/day sales and effective sale prices, gross/net receipt completeness, receipt assignments, opening/count evidence, pending order quantities and the explicit purchasing scope. All effective sale calculations use `effectiveSales`. The checklist shows missing information; no gross purchase total is represented as net consumption or profit. `resultCents` remains null with the explicit reason that net sales, deposits and valued consumption are not fully separated. Check completeness and economic-result availability are distinct.
- `event.close {eventId,revision,confirmedScope,note}` requires a nonempty review note, an exact current revision and owner closure capability. It may record a deliberate review with open points; those points and known/unknown values remain in the immutable snapshot. `event.reopen {eventId,reason}` requires owner permission and a reason, and is a separate transition before any corrections. A reopen cannot carry an economic or configuration edit in the same candidate. `lesson.add {eventId,text}` appends an owner-only lesson. Closed events must be reopened before adding a lesson or changing business facts. Creating a new event from a closed source preserves that source and starts with empty closure history.
- `closureHistory` records close/reopen action, reason, revision and the checklist snapshot. Microsoft server stamping supplies actor/time/operation/revision, including for new lessons. The UI labels local unconfirmed actor/time honestly. Closure checklist and history/lessons are reachable in Analysis.

## Reports and immutable orders

`buildEventExport(state,scope)` returns event identity, explicit scope, current revision, creation time, checklist/open values, source file/hash references and report rows. CSV uses semicolon quoting and neutralizes spreadsheet formula prefixes; null is exported as `Offen`. Printable standalone HTML carries the same metadata and source references, escapes user text and uses a repeatable print header/table. Users open that file and print/save PDF through their browser. No PDF engine or unverified automatic PDF generation is claimed. Reports visibly say they are not a full backup.

`orderCsv(order, exportRevision, createdAt)` uses only the immutable order's header and row facts. Missing historic context remains open. Export revision and export time are explicitly distinguished from saved-order creation time; old snapshots never recorded an original order revision, so exports say `Bestellrevision historisch nicht erfasst`. Order preview includes this provenance and truthful manual ordered/confirmed status. The deferred Task 3 audit-stamp issue is fixed by rendering the existing shared stamp on its own line.

## Backup contract and current product limits

`KitchenBackup` formatVersion **1** contains environment/workspace ID, workspaceRevision, createdAt, canonical state including archives/history/IDs/signatures, settings, nullable documents/drafts/operationReceipts, original manifest, raw workspace evidence, explicit missing/completeness status and a whole-packet SHA-256. Actual receipts preserve their persisted row ID, workspace relationship, original request hash, actor, applied revision, recorded time, raw row and RowVersion. A receipt hash is never presented as reconstructed original RequestJson bytes.

`buildKitchenBackup(source)` requires owner authorization before reading and rechecks authorization. Two complete source reads are hashed including row sets, raw state, metadata, versions and original evidence; any observed difference rejects the capture. This is drift detection, not an atomic cross-resource snapshot or substitute for a coordinated write pause. Exact persisted state text and its UTF-8 hash are retained, as are raw workspace and operation rows. IDs/relationships, canonical event uniqueness, table/read status, packet/aggregate bounds, receipt completeness, source originals and hashes are checked. Complete source adapters must supply genuine verified evidence, not an assertion from an untrusted browser.

Unknown source tables are **null**, never fabricated empty arrays. Empty arrays mean the source actually read as empty. Nonempty future document/draft tables deliberately remain incomplete pending Tasks 5/6's versioned table/relationship extension. Historical source references (including archives/baselines) require actual original bytes or a separately retained backup verified at the same hash/version; a link-only manifest is incomplete. Referenced local originals are not assumed to exist in SharePoint.

Current in-app integration is deliberately an **owner-gated incomplete snapshot**. `buildRepositoryBackup` calls the existing repository's canonical Load twice, checks stable identity/capabilities and downloads an explicitly named incomplete JSON file from Settings. Its document, draft and actual operation-receipt sources are null; raw workspace evidence is null. It does not synthesize receipts from operationIds or signatures and does not expose backup capability to a report reader. Legacy local schema 1 remains unsupported by this versioned backup contract, without editing that file.

**Remaining product integration:** a verified owner-gated actual snapshot source for **every operation row and full raw workspace evidence**, plus later document/draft rows, versioned original inventories and bytes, is still needed for a usable **complete in-app backup**. The existing Load endpoint cannot supply these missing sources. Bounded provider paging, effective owner authorization, coordinated capture, package/client/schema/configuration release evidence and actual row/original collection belong to Tasks 5/7 and the reviewed release tooling. This task does not claim that a real complete backup has been taken.

`tools/backup-restore/restore.ts` provides only a bounded, explicitly authorized **isolated local test** path. It checks format/hash/completeness, invokes the fixed offline production C# closed-schema validator, refuses existing targets and .local-state/.git paths, creates a private new directory, writes the package and safe indexed original files, and independently reads them back. It does not accept arbitrary restore commands or URLs and is not imported into production App. Separately retained originals must first be materialized as verified bytes; a reference-only restore fails. Default bounds are 512 KiB aggregate, 64 MiB packet and 20 MiB per embedded original; overflow stops rather than trims. Its C# validator must be freshly built before running the local restore tests; stale/missing binaries fail closed.

**Actual Microsoft restore remains a distinct required release gate.** No separately authorized Dataverse/SharePoint test target is wired, no cloud restoration was run, and no environment/app/trial/grant was created. Local synthetic restoration is local evidence only. See `tools/backup-restore/README.md` for contract and harness details.
