## Transaction and guard handoff

`ReceiptIntake.Prepare` performs only reads/validation and creates candidate data in memory. It verifies actual caller, workspace/event, open event, exact draft RowVersion, all linked source rows/versions/hashes/review flags, reviewed fields/raw text and decisions. Before any persistence, normal Protocol.Commit requires the ambient synchronous transaction and workspace RowVersion. The sequence is draft CAS, existing workspace CAS, existing immutable operation receipt create, all through the actual caller's IOrganizationService inside that same context. Storage faults escape; no catch converts a partial failure into success/rejection. No Web API self-call, ExecuteMultiple/ExecuteTransaction or second intake writing path exists.

The document guard adds one narrowly bound Update path for receipt.draft.accept. It checks the immediate own synchronous API context (or one matching platform wrapper), caller, workspace/event/target, draft RowVersion, accepted payload/snapshot, exact request hash/operation ID, actor and timestamp. Direct/bulk/wrong-parent/wrong-ID/wrong-version/wrong-actor/extra-field/payload substitutions reject. Normal invoice.save cannot attach new intake provenance. Accepted drafts cannot return to editing; later economic changes use the established receipt correction path.
