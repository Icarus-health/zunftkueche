## Local change and resolved capacity decision

Added drift diagnostics to ResourceEngine.EnsureAsync: a mismatch records the already source-defined resource name, existing fixed error code and an allowlisted field path, e.g. `$.MaxLength` or `$.RequiredLevel.Value`. The allowlist prevents arbitrary property names from becoming diagnostic text; unknown expected keys become `field`, and array paths use `[]`. Remote values, expected payload values, tokens, provider body text and seed/package content are never emitted. RequireMatch retains exact leaf equality, required-field checks and exact array lengths/order. Existing extra managed-property fields remain accepted as before. No write, overwrite, retry, publishing or drift-tolerance capability was added.

The reason the create request's 200 became 850 remains undocumented; the implementation makes no universal platform-normalization claim.

Root explicitly authorized changing only the two internal zk_name capacities from 200 to **exactly 850** in the pinned registration contract. That local contract change is now implemented, with SHA256 pin **08bd35ddbb43f12ee2c80eed9048630bebf25a899d012a327db3aa9f647baf47** (previous 46e7fe2b0a71763318bd713df028c3e57ed7d8a7fae380566622a44f94017207). Business state text limits, zk_state capacity, operation ID/hash/actor limits, source/domain/plugin/package code, six guards and ten runtime gates remain unchanged. This is an environment-specific internal label contract choice, not broader business-data tolerance.

## Relationship create-shape follow-up

Base for this follow-up: d570202. Root then explicitly initiated attempt 70910 after that readback; it reused the tables and attributes exactly, but returned the same relationship error and missing canonical readback. Each write attempt stopped safely. The second occurrence after independent visibility checks weakens a short table-visibility-delay explanation; it does not prove which object the service failed to resolve.

The official [Web API relationship creation documentation](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/create-update-entity-relationships-using-web-api) states that Lookup creates the lookup column together with the relationship through deep insert. Its request supplies ReferencedEntity, ReferencedAttribute, ReferencingEntity and Lookup.SchemaName, but omits ReferencingAttribute. It expressly allows a custom ReferencingEntityNavigationPropertyName. The official [SDK CreateOneToManyRequest example](https://learn.microsoft.com/en-us/dotnet/api/microsoft.xrm.sdk.messages.createonetomanyrequest?view=dataverse-sdk-latest) likewise defines the new column in Lookup and omits ReferencingAttribute from relationship metadata. The [OneToManyRelationshipMetadata reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/onetomanyrelationshipmetadata?view=dataverse-latest) describes ReferencingAttribute as the referencing column name; it does **not** document that supplying it forces existing-column resolution. Therefore that mechanism remains a hypothesis, not an established platform fact. No claim is made that the local tests reproduce Dataverse's internal 404 cause.
