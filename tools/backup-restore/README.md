# Kitchen backup contract v1 and isolated restore

`src/data/backup.ts` exports `buildKitchenBackup`, `validateKitchenBackup` and `buildRepositoryBackup`. This is a structured **business-data** backup, separate from CSV/HTML/PDF reports and later release/package/configuration evidence.

A provider adapter must verify owner authorization before its first read and again before its final read. It supplies the canonical aggregate (never an event projection), exact persisted workspace JSON and hash, raw workspace row, revision/RowVersion/owner, actual operation rows with all persisted fields and IDs/RowVersions, settings, document/draft tables and an original manifest. Both complete reads are fingerprinted, including original bytes and versions. Cross-resource brackets detect drift; they do not replace a coordinated write pause or create an atomic SharePoint/Dataverse snapshot. Release work still owns bounded same-origin paging, actual effective rights, metadata/package inventory and source capture.

`null` for documents/drafts/receipts means unread, not empty. A confirmed empty collection is `[]`. The current App adapter can only read the aggregate via existing Load: it intentionally downloads an **incomplete** packet for owners, with all three unavailable sources null and workspace raw evidence null. It never synthesizes operation receipts from `operationIds` or signatures. The exact original request bytes cannot be reconstructed from a receipt hash. Local legacy schema 1 is rejected; this path does not migrate or rewrite it.

Nonempty future document/draft tables remain incomplete until Tasks 5/6 extend the versioned schema and relationship validator. Historical source references are inventoried recursively, including archive and invoice baselines. Links do not qualify as original backups. Each original needs actual bytes with SHA-256 or an independently retained backup with matching hash and version plus a recorded verification. The provider adapter is responsible for obtaining genuine retained-backup evidence, not accepting unverified browser assertions. Existing original paths remain source material, not cloud-presence proof.

## Local-only restore

1. Build the current `server/Tests/Kitchen.Policy.Tests.csproj` using the existing net8 runtime and cached dependencies (or run the existing `npm run build:server`). No SDK install is needed.
2. Call `restoreLocalTest(backup, {kind: 'isolated-local-test', directory: NEW_DIRECTORY, authorized: true})` from the offline harness. There is deliberately no production App import route, provider restore action, arbitrary command argument or source overwrite option.
3. Before creating the new target, validation checks version, whole-packet hash, aggregate bounds, IDs/references, actual receipt relationships and completeness. The fixed offline C# entrypoint invokes the production closed-schema policy, including all nested record schemas. Existing targets and `.local-state`/`.git` targets are rejected. A missing/stale validator binary fails closed. Temporary validation files are created privately and only that generated temporary folder is removed.
4. The package is saved mode 0600 in a newly created mode 0700 directory; original binary filenames use numeric indexes, never untrusted paths. Packet and original bytes are read back independently. Separately retained originals must first be materialized as verified bytes; the harness rejects a reference-only restore.

The result is `local-isolated-restore-verified`, with `microsoftRestore: 'not-tested'`. It is not provider restore acceptance. No separate authorized Microsoft test target is currently wired. Actual Dataverse/SharePoint restore, privileges, transaction behavior, complete table capture and cross-user replay remain later release gates. Do not create an environment, app, trial or grant to bypass that gate.

Bounds: 512 KiB aggregate, 64 MiB packet, 20 MiB per embedded original. A larger source needs a reviewed separated-original backup workflow; bounds must not truncate records. IDs, historical snapshots, corrections, canonical event order, receipt actors/hashes/revisions and aggregate operation signatures are retained verbatim.
