# Fixed Zunftküche release foundation

This tool is preparation, not an approved or completed native release. Existing Microsoft tenant, environment, solution, package, app and workspace are fixed in copied contracts. No role, owner, environment, app, restore, publication or original-file deletion operation is exposed.

Default `plan` is offline and constructs neither authentication nor transport. The direct executable validates fixed contract factories; the independent Python gate additionally validates source/build/.NET host/client manifests. Unknown and combined mode arguments refuse. Modes are separate invocations: `inspect`, `backup`, `provision-document-schema`, `activate-package`, `register-document-guards`, `verify-release`. There is no deploy-all command.

## Independently reviewed launch

A reviewer must first hash-check **prelaunch.py** against an independently retained literal hash using Python stdlib, and only then execute it with `python3 -I -B`. Supply separately reviewed literal hashes using `--source-sha256`, `--build-sha256`, `--host-sha256`, `--client-sha256`; omit `--mode` for the fully offline plan. These manifest files reside here, but their own contents never establish trust. Source/build manifests bind exact file lengths/hashes and the source-to-build link. Source scope and compile/resource lists are literal in the gate. The host manifest pins the local dotnet binary and exact host/fxr + Microsoft.NETCore.App8.0.32 contents; roll-forward and runtime injection are disabled. The client manifest pins root config, all source/generated/binding files and exact dist contents; the gate verifies the existing app/environment identity. Never repin historical deploy tools.

Only after external source/build/runtime review may the parent select `--mode inspect` or `--mode backup`. Authentication preserves the accepted PKCE public-URL handoff and fixed identity checks, with no token/CLI/browser-cache persistence. `inspect` captures current metadata, old exact intrinsic/API checks, new table discovery, bounded complete pages, raw responses, current raw state and receipts, roles and routes. A missing lookup is not an empty store. Metadata/table/read errors stop. Native inventory is not a server-issued backup and never invents `sourceContract`.

`backup` uses the same fixed read-only capture path and attempts retained originals from `review/originals-manifest.json`, independently pinned with `--originals-sha256`. `OriginalVersion` records have PascalCase fields as in the contract. Original requirements are derived from fresh raw aggregate state and every document/draft payload history. Local imports retain local provenance and exact source hash. Any cloud version or unresolved source forces Incomplete, even when a truthful retained local import has the same hash. The supplied hash list can only corroborate the derived local requirements. Verified local originals and their manifest remain retained as historical evidence if cloud requirements block completion. Paths are relative to the fixed private `review/` folder. Retained raw state is not normalized or trimmed; final compiled pure policy runs on a parse/copy. Core capture returns fingerprints tied to the named raw-state/workspace/receipt artifacts. Extended stores, original verification and completeness facts run inside a connected bracket that requires the same core facts before and after them; drift in the core-to-extension gap stops completion and preserves the earlier files. Backup returns Complete only with a separately literal-pinned current-source visibility review matching the fresh workspace/receipt/store/access fingerprints and exact installed-store coverage, plus verified original bytes. A pre-schema backup can cover only the installed workspace/operation stores; absent new stores do not require future editor grants. With the current empty visibility-review pin it returns Incomplete. Future two-editor document acceptance remains separate. Keep all capture files private; a retained inspection manifest is not permission to mutate.

Mutating phase and package-transition catalogs are deliberately empty. No diagnostic/final hashes, native IDs or evidence were invented. Attempts stop before authentication. Adding a literal phase/transition/binding is a separate source review with a fresh checkpoint, review and exact package/build/source proofs. Typed phase dispatch, fixed metadata/payload/route contracts, additive independent-readback semantics and package adapter are implemented. Each literal schema phase selects exactly one table/column/relationship/membership operation; each guard phase selects one binding. Checkpoint remeasurement verifies retained manifests plus current state/receipts/stores/metadata/access/roles/client closure and local original bytes. Cloud originals currently fail closed because a fresh fixed SharePoint version-byte reader is not implemented; no retained-local proof is promoted to current cloud evidence. Fixed eligibility reads use documented CanBeReferenced/CanBeReferencing Actions and both GetValid... Functions, with complete competing-parent inspection. Fixed missing-only AddSolutionComponent binds canonical MetadataId/component type and no required/subcomponent expansion. These request contracts are implemented; native response shapes remain unproved. `verify-release` has a separate reviewed final-package pin and a fixed read-only server-backup adapter; its currently absent pin stops before authentication. It cannot turn inspection into green release status.

Each additive target now has a distinct exact-object read and a separate enclosing collection read. Fixed metadata alternate keys and subtype casts identify tables, columns and relationships. Solution components and guard steps first use a fixed 0/1 target lookup, then GET the observed server GUID; no GUID is guessed. Full returned values (including unknown fields) and primary-name/lookup companion metadata are compared on copies; raw responses remain retained. Only top-level OData context and the optional metadata type prefix are normalized for comparison. A failed or late exact read cannot become absence or success.

Guard registration and package activation require a literal-pinned `Routes` file in their reviewed phase. `RouteReview` binds the fixed organization/solution and every route to authoritative evidence. Final accepting activation requires `FinalWitnessed` review with actual retained native-witness files for the complete mandatory and discovered route matrix. Files are checked before authentication; the full disposition validator runs against fresh filters and global steps before dispatch and again in the immediate checkpoint. Missing, duplicate, extra or unsafe route dispositions stop before writes. C/U/D must have individual guard dispositions. Pre-schema creation does not require witnesses for future tables.

The separate `RefusalPreparation` type applies only to the fixed v5-to-refusal-diagnostic transition or a bounded initial guard registration with `PreparationContract`. It retains the complete fresh metadata/disposition plan with an exact inventory fingerprint; unproved witnesses have explicit `Unproved` state and null file/hash, never placeholders. It requires the exact diagnostic bytes/source-build, independently reviewed proof that ordinary KitchenCommit refuses before write and document acceptance is disabled, and an ordinary-use/source/package-writer exclusion proof bound to the phase review and checkpoint. Before a preparatory guard write the currently installed package metadata/bytes must stably match that diagnostic. There is no general skip flag and no supervisor/return-to-use implementation. The tool verifies independently reviewed, literal-pinned exclusion/refusal evidence; it does not itself disable users or prove such operational exclusion. These real proofs, package artifacts and catalogs are still absent, so preparation remains unexecutable. Its success status would describe only refusal preparation, never final release readiness.

Current-source inspection and checkpoint share the same incremental schema handling. A primary-name-only table includes the mandatory generated primary GUID and system attributes. `contracts/user-owned-system-shape.json` supplies a closed historical UserOwned system-shape candidate (31 system fields plus one primary shape), derived from the parent’s nonprivate historical metadata extract. The two primary logical IDs are fixed explicitly; SchemaName casing and metadata IDs are retained from the new native response and are not invented from the historical table. Missing/changed system fields, wrong primary type/name or unreviewed extra fields stop; actual new-table metadata remains a native review gate. A table can be classified as Partial only when every present fixed object is exact, custom/secured/parent metadata has no unknown or drift, and a bounded unfiltered all-table query returns zero rows. It never filters on a not-yet-created workspace column. Partial nonempty tables stop; partial metadata never satisfies final package/guard exact-schema requirements. Complete backup still requires the separately reviewed complete-read coverage of every installed store, including partial tables. The explicit status is `PartialInstalledEmptyVisibilityNotProvenComplete` until that visibility review exists.

Operator lifecycle: one reviewed operation per mode is active in `ReviewedRelease.Phases`; there is no runtime operation selector. After an observed phase, retain its attempt/observations and capture/review the fresh state. Prepare and independently review the next literal operation, new plan/checkpoint pins, source/build closure and launcher pins; then invoke that mode once. Replacing a catalog entry is a new reviewed source change, not permission to retry an old operation. Preserve old attempt journals. Duplicate entries for a mode fail closed.

Before every attempted write, persist and flush a private CreateNew attempt marker. Every prior attempt, including a timeout or old-looking readback, blocks restart mutation; local exclusion is not a global provider lock. Content update is at most once, with strict ETag CAS or separately reviewed coordinated-writer mode; no fallback, retry, rollback or data rewind. Write deadline90s, independent readback180s with each read60s; tokens are independent of caller cancellation. Provider result codes alone never prove success. Preserve observations and partial resources.
