# Dedicated document and manual draft source contract

Source proposal only. No table, relationship, role, plugin registration, connection grant or publication has been performed by this task. `schema-proposal.json` is additive release input, not a script to apply blindly. Historical Deploy/Access/Acceptance/PackageUpdate sources remain pinned.

Both new tables are UserOwned, caller-created. A native primary UUID is the immutable unique key. They reference the workspace through `zk_workspace`; all DTO IDs/events are checked against the actual caller's workspace, and all updates use Dataverse RowVersion CAS. Neither table writes the 512 KiB kitchen aggregate. Validation-only rejection returns status rejected before the persistence boundary; storage faults after writes start escape. Each payload preserves bounded immutable snapshots with the actual actor and UTC time. Record history growth fails explicitly before 128 KiB; no truncation or rotation deletes evidence.

Read requires actual workspace Write access plus the caller's effective new-table access. A report reader receives no new-table privilege. Basic Read/Write/Create/Append on these UserOwned tables still needs actual owned/shared row access. Parent Share/Unshare/Reparent cascades are a **candidate** for both editors' reciprocal access, not proof. Creator ownership is retained; no Assign/Share privileges, organization-wide new-table Read, SYSTEM execution or service-owner fallback are proposed. Direct table retrieval is possible with effective record Read and must be tested independently from API filters. Inherited-right cleanup can lag or fail. Unknown or security-trimmed inventories cannot constitute a live full-backup acceptance.

## Frozen Task6 interface

Existing `zk_KitchenLoad` and `zk_KitchenCommit` are reused; protocolVersion remains 2 and identity remains `{organizationId,userId,workspaceId}`. Load `{protocolVersion,workspaceId,identity,view:"documents"}` returns caller-authorized `documents` and `drafts`. This view is distinct from the owner-only backup view.

Document mutation envelope: `{protocolVersion,workspaceId,identity,view:"documents",action,requestId,value}`. Actions are only `upload.begin`, `upload.claim`, `upload.link`, `draft.save`. `requestId` is a stable UUID and exact request hash+actor replay is retained per-row in history. Begin supplies immutable UUID-v4 uploadId, eventId, principal, sha256, mimeType, size, originalName. Claim requires current rowVersion and permits exactly one selected->uploading transition. Link adds provider-specific `DocumentRef` after external verification. No original bytes enter Dataverse. Empty/unknown external outcomes retain the reservation; no automatic deletion or repeated CreateFile. Draft schema is exported in `src/data/documents.ts`. Pages are ordered **whole originals**; a PDF's internal page count is unknown, no cut occurs. A manual draft has no parser/model/prompt version, and each source retains documentRowVersion, external ETag, hash and explicit originalReviewed flag. Header/line unknowns stay empty/null.

Task6 must add only `receipt.draft.accept` to the existing synchronous normal KitchenCommit transaction: require actual initiating caller, exact identity/workspace/event, expected aggregate revision, draft RowVersion and every document RowVersion+original version/hash. Validate linked originals, reviewed state, and business invariants server-side. Draft acceptance update, aggregate CAS and immutable operation receipt must share one ambient Dataverse transaction; explicitly require IsInTransaction before any write. Update the dedicated guard with exact new Task6-origin target binding as a separate reviewed change. No client-only acceptance, direct invoice.save bypass or separate write sequence is authorized here. External SharePoint bytes/ETag/hash checks are fresh observations, never atomic with Dataverse. A RowVersion is not proof of unchanged SharePoint content. Use SDK calls within the synchronous plugin; no Web API, ExecuteTransaction or ExecuteMultiple inside it.

## SharePoint and bounds

Exact generated services and binding come from the already verified existing-app staging directory. Native siteCollectionId/webId/libraryId/itemId/ETag and connector path identifier are named accurately; no Graph driveId is invented. Every provider boundary checks host identity, connector currentuser (all meaningful principal observations), native destination, and versioning. Reads compare metadata before/after and original SHA-256.

5 MiB per original, 10 ordered originals, 20 MiB bundle; JPEG/PNG at most 24 million pixels and 8192 pixels per side, checked from bounded bytes before browser decoding. These are proposed conservative safety limits, not device/host performance proofs. PDF pages remain unknown without a proven parser. HEIC and corrupt/unsupported headers are rejected with export guidance. Browser decoding can still reject corrupt compressed data; UI must show a clear failure. OCR is disabled.

Generated CreateFile has no overwrite=false parameter. Persistent server CAS permits one app create at a UUID-derived reserved name after an exact-path absence check. Retries only find/hash-check that same path. Concurrent external creation of precisely that UUID path remains a cross-provider race; no conditional SharePoint creation or no-overwrite atomicity is claimed. No original filename is used as the storage key. Ambiguous missing files stay blocked for investigation.

## Task 5 fix round 1 — response, editing and backup handoff

The documents view still uses protocolVersion 2 and `identity: {organizationId,userId,workspaceId}`. Successful mutation responses now have `outcome: applied | replayed | existing`, `value` (the current row with its current RowVersion) and `acknowledgment` (an immutable copied history entry, or null for an existing reservation returned without a new mutation). A replay returns the matching historical acknowledgment **and** the latest row; these are intentionally different results. The history snapshot has no invented historical native RowVersion. Rejected responses retain their existing rejection envelope.

`DocumentStore.claim` returns `{row,createAuthorized}` internally. Only a continuation that freshly persisted that request and receives `applied` for its own `upload.claim` acknowledgment may call CreateFile. A resumed pending request is read-only even if its delivery is the first to reach the server and the response says `applied`. Replayed/existing responses never grant creation. A per-repository active-upload set also refuses overlapping continuations; separate runtime instances still depend on the persisted request and explicit server outcome. Pending cleanup compares the exact stored request before removal. Lost fresh acknowledgment can leave a reservation unresolved with no file; recovery never creates again merely because it reads absence. SharePoint still offers no verified conditional-create/overwrite protection here; an external actor creating the exact UUID path between absence read and create remains the separately accepted cross-provider limitation.

The manual editor retains controlled raw total, quantity and line-amount text alongside its draft. The initial/opened/acknowledged saved editor snapshot is its stable baseline. Header/line-first edits, removal of the last original, a queued file, and invalid or still-focused raw numbers all participate in the existing navigation/beforeunload guard. Parsing happens before save; rejection leaves raw text and baseline unchanged. The cancel control is exclusive to the upload flow with an AbortController; status/open/save expose pending status without promising cancellation of those calls.

The backup extension checks both tables' native primary ID, RowVersion, exact workspace lookup shape, event, payload, formatted metadata and custom actor/timestamp against normalized data and last history. The native write uses the same server history timestamp; the write guard rejects a different target timestamp. Backup timestamp comparison uses millisecond-normalized UTC instants while preserving both original serialized timestamps. Provider readback precision/shape remains a live gate.

Every retained document reference and every draft history snapshot participates in relationship/original-manifest checks. Missing original inventory relationships reject. Missing exact bytes/external-version evidence or unproved historical native RowVersion makes the backup incomplete. The current native RowVersion attests only its current reference, not every past snapshot. No provider historical-version endpoint or fabricated historical RowVersion was added. All raw native fields remain in the packet; hashes are consistency checks, not a signature of provider authenticity.

## Task 6 source extension — conscious acceptance

`receipt.draft.accept` is a **normal** KitchenCommit operation (no `view`). Its payload is `{eventId,expectedWorkspaceRevision,draftId,draftRowVersion,documentVersion,reviewedFields,reviewDecisions,operationId}`. `expectedWorkspaceRevision` equals envelope `expectedRevision`; both operation IDs and event IDs must agree. `documentVersion` is the saved ordered pages array, including each native document RowVersion, external ETag, exact SHA-256 and explicit originalReviewed. `reviewedFields` is the exact saved header and lines plus controlled `raw` number strings. `reviewDecisions` requires `receipt/fields/originals:true, prices:'separate', stock:'separate'`. It does not book stock or change prices.

The existing handler derives the only new invoice from the stored reviewed draft. CandidateState is not an alternate invoice override. Draft ID is receipt ID; an immutable `intake:{draftId,operationId}` reference lives in the first sourceBaseline and subsequent corrections. Gross line cents stay gross and net remains null. No old imported or accepted invoice is overwritten. Exact operation bytes+actor replay occurs before stale revisions and returns the existing applied revision with current workspace state. Changed bytes or actor under the same operation ID fail. The draft cannot be edited after acceptance. Existing same supplier/number denial stays stricter than the additionally checked supplier/number/date/amount duplicate; exact original hashes and draft identity are independently checked. Prior intake source rows must be accessible for duplicate checks; missing access fails closed.

Preparation reads actual current workspace/event, draft and source rows under the current caller, validates their binding, and creates the accepted draft/history and invoice candidate without writes. Before persistence it requires the existing ambient synchronous Dataverse transaction. It writes the draft with native RowVersion CAS, then calls the existing workspace CAS + immutable operation receipt store. Any storage fault escapes; no same-organization Web API or nested batch transaction is used. The dedicated draft guard admits only the exact bound Update, immediate own API context (or one matching platform wrapper), actor, RowVersion, fields, accepted payload, snapshot, operation hash and timestamp. No direct or alternate intake write route exists. Native step registration/target decorations and real rollback remain parent release gates.

Manual draft saves optionally preserve `rawInput` and `textAssist`; history retains earlier values. The optional helper accepts at most 16,000 explicitly supplied text characters, stores raw text, `origin:user-supplied`, `completeness:unknown`, parser version, proposals and exact offset quotations with `page:null`. It never reads the clipboard automatically or claims text came from the linked original. Proposal selection changes one manual field; the user must review originals again and save before acceptance. Unsupported line layouts, credits/discounts/tax groups stay manual; negative suggested totals cannot enter the nonnegative receipt domain through this helper. Parser proposals never create operations.

PDF/image engines remain deliberately unavailable. Worker/WASM host evidence is negative; Node PDF preflight does not prove responsive or hard-cancellable browser execution. AI Builder, Copilot Studio and Azure are off; the read-only 2,500-credit snapshot is not permanent free entitlement or a verified invocation route. No new package, provider, flow, connector, key, credit allocation or paid fallback was added.

The same `kitchen-documents-v1` backup contract now requires accepted drafts, complete raw/history/native rows, original manifests, matching operation receipt and signature, and the immutable invoice baseline. A document-bearing accepted state cannot downgrade to core. Imported packets validate every retained snapshot, raw text evidence, raw number correspondence, acceptance decisions and native audit metadata. Full local isolated restoration is tested; hashes prove internal consistency only. No provider-side complete inventory, historical native versions, actual ACL isolation, 30-receipt benchmark, mobile responsiveness or Microsoft restore is implied. Fresh SharePoint metadata/bytes reads before acceptance remain separate observations; they do not join the Dataverse transaction.
