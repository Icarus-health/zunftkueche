# Dedicated document and manual draft source contract

Source proposal only. No table, relationship, role, plugin registration, connection grant or publication has been performed by this task. `schema-proposal.json` is additive release input, not a script to apply blindly. Historical Deploy/Access/Acceptance/PackageUpdate sources remain pinned.

Both new tables are UserOwned, caller-created. A native primary UUID is the immutable unique key. They reference the workspace through `zk_workspace`; all DTO IDs/events are checked against the actual caller's workspace, and all updates use Dataverse RowVersion CAS. Neither table writes the 512 KiB kitchen aggregate. Validation-only rejection returns status rejected before the persistence boundary; storage faults after writes start escape. Each payload preserves bounded immutable snapshots with the actual actor and UTC time. Record history growth fails explicitly before 128 KiB; no truncation or rotation deletes evidence.

Read requires actual workspace Write access plus the caller's effective new-table access. A report reader receives no new-table privilege. Basic Read/Write/Create/Append on these UserOwned tables still needs actual owned/shared row access. Parent Share/Unshare/Reparent cascades are a **candidate** for both editors' reciprocal access, not proof. Creator ownership is retained; no Assign/Share privileges, organization-wide new-table Read, SYSTEM execution or service-owner fallback are proposed. Direct table retrieval is possible with effective record Read and must be tested independently from API filters. Inherited-right cleanup can lag or fail. Unknown or security-trimmed inventories cannot constitute a live full-backup acceptance.

## Frozen Task6 interface

Existing `zk_KitchenLoad` and `zk_KitchenCommit` are reused; protocolVersion remains 2 and identity remains `{organizationId,userId,workspaceId}`. Load `{protocolVersion,workspaceId,identity,view:"documents"}` returns caller-authorized `documents` and `drafts`. This view is distinct from the owner-only backup view.

Document mutation envelope: `{protocolVersion,workspaceId,identity,view:"documents",action,requestId,value}`. Actions are only `upload.begin`, `upload.claim`, `upload.link`, `draft.save`. `requestId` is a stable UUID and exact request hash+actor replay is retained per-row in history. Begin supplies immutable UUID-v4 uploadId, eventId, principal, sha256, mimeType, size, originalName. Claim requires current rowVersion and permits exactly one selected->uploading transition. Link adds provider-specific `DocumentRef` after external verification. No original bytes enter Dataverse. Empty/unknown external outcomes retain the reservation; no automatic deletion or repeated CreateFile. Draft schema is exported in `src/data/documents.ts`. Pages are ordered **whole originals**; a PDF's internal page count is unknown, no cut occurs. A manual draft has no parser/model/prompt version, and each source retains documentRowVersion, external ETag, hash and explicit originalReviewed flag. Header/line unknowns stay empty/null.

Task6 must add only `receipt.draft.accept` to the existing synchronous normal KitchenCommit transaction: require actual initiating caller, exact identity/workspace/event, expected aggregate revision, draft RowVersion and every document RowVersion+original version/hash. Validate linked originals, reviewed state, and business invariants server-side. Draft acceptance update, aggregate CAS and immutable operation receipt must share one ambient Dataverse transaction; explicitly require IsInTransaction before any write. Update the dedicated guard with exact new Task6-origin target binding as a separate reviewed change. No client-only acceptance, direct invoice.save bypass or separate write sequence is authorized here. External SharePoint bytes/ETag/hash checks are fresh observations, never atomic with Dataverse. A RowVersion is not proof of unchanged SharePoint content. Use SDK calls within the synchronous plugin; no Web API, ExecuteTransaction or ExecuteMultiple inside it.

## SharePoint and bounds

Exact generated services and binding come from the already verified existing-app staging directory. Native siteCollectionId/webId/libraryId/itemId/ETag and connector path identifier are named accurately; no Graph driveId is invented. Every provider boundary checks host identity, connector currentuser (all meaningful principal observations), native destination, and versioning. Reads compare metadata before/after and original SHA-256.

5 MiB per original, 10 ordered originals, 20 MiB bundle; JPEG/PNG at most 24 million pixels and 8192 pixels per side, checked from bounded bytes before browser decoding. These are proposed conservative safety limits, not device/host performance proofs. PDF pages remain unknown without a proven parser. HEIC and corrupt/unsupported headers are rejected with export guidance. Browser decoding can still reject corrupt compressed data; UI must show a clear failure. OCR is disabled.

Generated CreateFile has no overwrite=false parameter. Persistent server CAS permits one app create at a UUID-derived reserved name after an exact-path absence check. Retries only find/hash-check that same path. Concurrent external creation of precisely that UUID path remains a cross-provider race; no conditional SharePoint creation or no-overwrite atomicity is claimed. No original filename is used as the storage key. Ambiguous missing files stay blocked for investigation.

## Backup

Actual Dataverse store always publishes `kitchen-documents-v1` with required document/draft inventories and manifestVersion1, including actual empty arrays. Missing tables/rights fail; they cannot silently become the old core contract. It rereads workspace, operations, documents and drafts to reject observed drift. Client capture fetches original bytes with the current caller, checks version/hash, and preserves raw rows, histories and references. An unknown/unlinked upload or missing original stays incomplete. Historical kitchen-core-v1 packets remain a historical core scope, not a complete document-bearing deployment. Local isolated restore is only local evidence; separated Microsoft restoration and live inventory completeness remain later gates.
