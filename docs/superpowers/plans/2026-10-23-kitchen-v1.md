# Kitchen v1 Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. The user has explicitly requested implementation of the approved design in this chat.

**Goal:** Deliver a working first kitchen administration app in Teams channel Küche without new paid services.
**Architecture:** Add a product web part beside the existing probe. Typed pure domain functions validate entities and order snapshots; a small SharePoint adapter persists seven app-owned lists using ETags and committed order revisions. A native, responsive UI renders the approved four views.
**Tech Stack:** Existing SPFx 1.23.2, TypeScript, native HTML/SCSS, SharePoint REST with SPHttpClient.
**Spec:** docs/superpowers/specs/2026-10-23-kitchen-v1-design.md

## Global Constraints
- No added paid services, new access grants, automatic messages, deletion, public push or migration of existing data.
- Preserve the probe and legacy application. Production and synthetic acceptance lists are separate.
- Save success requires readback; ETag conflicts must surface; orders never silently overwrite newer orders.
- Prior-year drafts preserve source references, not source status/current prices/delivery/stock.

## Review Focus
- Repeated/uncertain order writes and staged partial revisions must not expose incomplete orders.
- Masters changed or deactivated after ordering must not rewrite historical snapshots.
- Decimal-comma quantities, missing values and pack conversions must remain explicit.
- Repeated prior-year copying and inactive/missing referenced entities must not create duplicate or invalid orders.
- Same-site URLs, paging, malformed payloads and unsupported schema must fail clearly rather than leak or truncate data.
